# Regras do projeto JMG Obras

Desenvolvimento direto pelo GitHub (sem Lovable). Trabalhe em branches e abra PR para a `main`; o CI precisa passar. Merge na `main` faz o deploy automático na VPS (`.github/workflows/ci.yml` publica as imagens no GHCR e roda `infra/vps/deploy.sh`; guia em `docs/deploy-vps.md`). O `infra/.env` de produção é montado pelo workflow a partir das variáveis/segredos do GitHub: configuração nova de produção entra lá e no workflow, nunca só na VPS.

Roteiro de melhorias priorizado (tarefas R1-1, R2-1…, com critério de pronto e dependências) em `claude/roteiro.md`; ao concluir uma, marque `[x]` e registre em `claude/contexto-desenvolvimento.md`.

## Project rules

- All price/margin math lives in `src/lib/pricing.ts` (pure, tested in `pricing.test.ts`); UI and PDF only call `computeBudget` — never duplicate formulas.
- Budget items snapshot catalog costs/composition (jsonb `materials`) so catalog edits never silently change existing budgets.
- Cost data access is enforced by RLS via `public.can_see_costs()` (admin/financeiro); roles live in `user_roles`, never on profiles.
- Approved/refused/superseded budgets are locked by DB trigger; changes go through "Reabrir para edição" (`copy_budget(id, true)` revisions, reusing an open newer revision via `openRevision`). Approving a revision (trigger `supersede_previous_budget`) atomically marks the previous approved version `substituido` (`superseded_by`), moves the linked work's `linked_budget_id` and stage sections to it, and is refused when that work has a signed contract (use extras instead).
- Works use the shared record trash (`manage_record_deletion` with `work_registry`): trashing also trashes the linked schedule header; permanent deletion is refused while financial, purchase, contract, record, extra or estimate links exist. Work list readers filter `deleted_at`.
- Client PDF is the official JMG model generated server-side by the API (`POST /v1/orcamentos/:id/pdf`, Playwright + pdf-lib in `api/src/pdf/`, Inter and logos embedded), rendered by default as ONE continuous page (A4 width, height measured from the content by `htmlToPdf`; no per-page header/footer, the company band closes the document) or, with `?layout=paginado` (`PdfLayout`/`pdfLayout` in proposal.ts, switch on `/orcamentos/$id/pdf`), as A4 sheets with each section on a new page and the header/footer stamped by pdf-lib on every page but the cover; `/orcamentos/$id/pdf` only displays it. It never renders internal costs/margins: data comes from pure `src/lib/proposal.ts` (`buildProposal`), shared by API and app, whose prices are sale values from `clientPriceSheet` in pricing.ts (each material gets its item's sale ÷ cost factor, rounded unit × qty; labor appears only as the total `saleNet − materials`, never per service or stage). Issue date = generation date, validity = `validity_date` or issue + 15 days, number `ORC-<year>-<0000>`, schedule from `budget_sections.start_week/duration_weeks` (`stageWeeks`), installments split in cents by `splitPayments` (remainder to the last) and the PDF is refused (422) until they sum 100%. Shared modules imported by the API (`pricing`, `proposal`, `extenso`, `documents`) stay dependency-free with `.ts` import extensions and are copied into the API image.
- The contract PDF (`POST /v1/orcamentos/:id/contrato`) uses the same identity and continuous page and only accepts `aprovado` budgets; its layout follows the 2026 JMG contract model (cover "Instrumento particular" with code `CT-<year>-<0000>`, parties + summary bar, numbered clauses, annexes, signatures and witnesses) and its clauses come from the editable model `contract_clauses` (Configurações → Contrato; admin edits, admin/financeiro read; migration `20261030000032` replaced the old CONTRATO.ELIANA text with the 2026 model) rendered in order by pure `renderClauses` in `src/lib/contract-clauses.ts`: one paragraph per line (`{{N}}.x.` number highlighted, `{{N}}.x.y.` indented, `I – ` incisos, `- ` items, `**bold**`), `{{N}}` = clause number, `{{OBJETO}}`/`{{ENDERECO_OBRA}}`/`{{AREA}}`/`{{ORCAMENTO}}`/`{{DATA_ORCAMENTO}}`/`{{VALOR}}`/`{{MAO_DE_OBRA}}`/`{{MATERIAIS}}`/`{{INICIO}}`/`{{PRAZO}}` inline and `{{TABELA_ETAPAS}}`/`{{TABELA_PARCELAS}}`/`{{DADOS_BANCARIOS}}` on their own line, all filled from the approved budget. Editing the model only affects contracts generated afterwards.
- work_registry is canonical for both origins; linked_budget_id alone references an immutable approved budget (only the supersede trigger may move it within the same budget family). Legacy works mirrors conversion atomically to preserve identifiers; direct works never insert budgets.
- Operational quantities and cash/allocations use pure tested helpers in operations.ts and work-opening.ts; economic price/result calculations stay in pricing.ts.
- Uploaded evidence and work documents use the private `jmg-documents` bucket and temporary signed URLs; team access is limited to operational records.
- Purchases create commitments atomically; partial receipts determine incurred purchase cost, while settlements affect only cash, never a second expense.
- Payment receipts (modelo `Recibo-JMG-modelo`): one receipt per incoming settlement of a work entry, generated by the API (`POST /v1/recebimentos/:id/recibo`, `api/src/pdf/receipt-html.ts`, continuous page) from pure tested `buildReceipt` in `src/lib/receipt.ts` (shared, dependency-free): number `REC-<payment year>-<budget number>-<installment>[-<settlement>]`, installment name without the " · work" suffix, %/when from the budget `payment_terms`, contract status up to the payment date (contract value = receivables only, never cash-only entries). Payer bank/account and transaction ID are optional request fields, not stored. The app page `/recibos/$id` shows/downloads it; every incoming settlement (with or without a work; general entries get no contract section) has a "Gerar recibo" button in Financeiro (caixa, contas a receber and Recebimentos e saldos), and registering one offers "Gerar recibo" in the toast.
- Every contract PDF generated from an approved budget (`/orcamentos/$id/pdf?doc=contrato`) is stored in `jmg-documents/contracts/generated/` and registered by `register_generated_contract` (one `contracts` row per work, new = `aguardando_assinatura`, signed never changes) so it appears in the Contratos menu (which also lists works with an approved budget and no registered contract, with "Gerar contrato", e.g. contracts generated before registration existed); statuses are `aguardando_revisao` / `aguardando_assinatura` / `assinado` (admin changes them; signing requires the signed document + date) via `ContractActions` (`components/management/contract-status.tsx`), shared by the Contratos list and the work Contrato tab (works with an approved budget use the official PDF; the text editor stays for legacy text contracts).
- Contract wording comes from the supplied model; saved bodies are snapshots and signed contracts/approved extras are immutable.
- Unconfirmed completion estimates retain the unregistered original budget cost; never interpret absent estimates as zero remaining cost.
- Work, contract, schedule, diary and extra changes append database audit snapshots in work_history so revisions retain authorship and prior values.
- Opening snapshots are immutable and separate from transactions and account balances; direct-work forecasts stay unconfirmed until a completion estimate is entered.
- Financial dashboard aggregation is shared by company and work views; economic results use pricing helpers, and installment payables never add a second purchase expense.
- Form drafts are scoped to the signed-in user and form on the current device; restore installment values but require users to reselect attachments.
- Draft capture and restoration use the shared form-draft helpers, including explicit unchecked values and file exclusion, so forms preserve selections consistently.

- The Painel (admin/financeiro) is `HomeDashboard` (`components/management/home-panel.tsx`): greeting header with Lançar entrada/saída (`/financeiro?novo=entrada|saida` opens the cash dialog) and Novo orçamento, compact filters, cash hero with period summary, last entry/exit, a receber/a pagar, active works and % received, monthly cash flow (realized + receivables by due date) and "Atenção" (overdue receivables, late stages, margin below minimum, unconfirmed cost, no schedule) from pure tested `src/lib/dashboard-home.ts`; work cards (`WorkCard`) have a navy band with the progress ring and Cronograma/Financeiro/Abrir obra shortcuts. Every number still comes from the executive.ts compositions, so cards and drilldowns match.
- Painel management indicators (roteiro R2-1/R2-2/R2-3) are pure tested `src/lib/business-indicators.ts`: `cashProjection` (today's cash + receivables − payables by due date over 13 weeks, from the all-period compositions; negative balance raises an "Atenção" item), `commercialFunnel` (latest revision per budget number, values from computeBudget via `commercialOptions`, refusal reason stored in `budgets.refusal_reason` and asked by `RefuseBudget`; `refusal_reason` is volatile for `budgetFingerprint`) and `delinquency` (overdue open receivables ÷ already due, value-weighted days late, ranking by client).
- Executive indicators and financial drilldowns use executive.ts compositions from dashboard-data; totals and source rows share one selector to prevent divergence.
- Relationship screens reuse relationship-data queries and navigate to existing work editors; the person profile route is unnested from the directory list to render independently.
- Record deep links use entry/record search parameters and use-record-focus to reveal the source without mutating transactions.

- Work progress/status comparisons live in pure tested work-progress.ts; shared dashboard progress preserves the immutable opening reference until weighted stages exist.
- Stage photos are existing work_records linked by stage_id, protected by same-work validation and private records paths; gallery and reports reuse these rows, so uploads are never duplicated.
- Individual work metrics use work-composition.ts to extend executiveComposition; signed economic breakdowns use the pricing result fields without recomputing economic formulas.
- Schedule headers identify all plans: standalone stages/versions live on schedules/schedule_versions until atomic linking moves stages with stable IDs and preserves immutable versions in work_stages/work_schedule_versions; linked plans always edit work_stages, never a second copy. Removed work stages remain for audit but all operational readers filter them out. Schedule date/status helpers are shared with client print views. The client schedule (work `/obras/$id/cronograma/pdf` and standalone `/cronogramas/$id/pdf`) and the work Cronograma tab use the JMG físico-financeiro sheets: `ScheduleSheets` (`components/works/schedule-sheets.tsx`, styles `.cr-*`, named page `cronograma` = A4 landscape) over pure tested `buildScheduleSheets` (`src/lib/schedule-sheets.ts`): 10 weeks per sheet from the Monday of the start week, the last sheet padded with grey weeks, stages outside a sheet shown as "concluída/inicia na Sx", only stages with planned dates; payments come from the work receivables (`financial_entries` entrada, not cash-only; admin/financeiro only) and client deliveries from `work_client_materials` (aba Materiais do cliente; team access like work_stages, audited in work_history). Linked schedule pages (`/cronogramas/$id` with a work) are the schedule dashboard (`components/schedules/schedule-dashboard.tsx`: indicators, 10-week grid from `buildScheduleSheets`, payments, client materials, revisions, "Lançar avanço"; stage structure editing stays in the work Cronograma tab) and the Cronogramas list is a dashboard too; their planned/realized/late/payment math is pure tested `src/lib/schedule-dashboard.ts` (realized = `physicalProgress`), and multi-stage date shifts go through `shift_work_stages` (one schedule revision). Work stages created from an approved budget get their dates from the budget schedule (`budget_section_dates`: budget `start_date` + section start_week/duration_weeks, same math as `stageWeeks`/`scheduleEnd`; trigger `work_stages_budget_dates` fills only empty dates). The work-contract print view prints as one continuous A4-width page via `printContinuous` (`src/lib/continuous-print.ts`).
- Enter submits forms through the global EnterToSubmit rule in enter-submit.ts (textarea only with Ctrl/Cmd+Enter); dialogs use SubmitForm with a type="submit" save button, every other button is type="button", and onBlur inline fields use commitOnEnter.
- CPF/CNPJ, RG, telefone e CEP são pontuados por `src/lib/documents.ts` na digitação, no salvamento e na exibição; campos de nome/endereço usam `capitalizeWordsProps` de `src/lib/text-case.ts` (maiúscula na letra digitada no início da palavra, partículas da/de/do minúsculas).
- Finance separates cash from accounts: `financial_settlements` are the realized cash movements and `financial_entries` the receivables/payables. Cash-only movements go through `register_cash_movement` (entry + settlement, `cash_only`), reversals through `undo_settlement`, cancellations through `cancel_financial_entry`; balances/status come from `cashSummary`/`accountStatus` in operations.ts.
- Stage services (`work_stage_services`) hold planned labor/material and progress; stages without services use the typed planned labor/material in `work_stage_values` (cost data, can_see_costs RLS, audited), which `stageCosts` ignores once services exist so values never double count; budget conversion (`convertBudgetToWork` → `convert_budget(id, services)`) creates one stage service per budget item with its COST (labor/material from computeBudget), mapped to its section's stage in the same transaction; an approved revision re-syncs them with `syncBudgetStages` → `sync_budget_stage_services` (lineage via `budget_items.origin_item_id` and `work_stage_services.budget_item_id`: updates cost/description keeping progress, adds new items/sections, deletes removed ones; manual services untouched); after conversion and after that sync, `applyValueWeights` sets each stage's weight ("Avanço % da obra") proportional to its planned value via the pure `valueWeights` (work-progress.ts, sums exactly 100%); stage progress is the value-weighted `servicesProgress` written to `work_stages.progress`, and stage spending comes only from finance outflows with `stage_id` via `stageCosts` — never a second manual cost field.
- Work checklist (`work_checklist_items`, aba Checklist da obra): each stage service becomes an item automatically via trigger `sync_checklist_from_service` (description/stage follow the service; deleting the service deletes the item), the team may add standalone items; RLS like work_stages (admin/financeiro/equipe) so the team never reads service costs; `checked_at`/`checked_by` are set by the database; checking never changes stage progress or finance. Grouping/counting use pure `work-checklist.ts`; the per-stage print view is `/obras/$id/checklist/pdf?stage=`.
- Budget pricing has two models chosen by `params.model`: absent = legacy markups (old budgets keep their values), `"custo_direto"` = new budgets. Price = direct cost (labor + materials) ÷ [1 − (structure + RT + taxes + target margin)]; `negotiated_price` overrides it; structure/RT/taxes are % of the final price and profit is the remainder (`priceFromCost`, `costBreakdown`, `marginLevel`, `priceSimulation` in pricing.ts). Materials go to the client at cost and client labor = final price − materials. Every open budget (elaboração/enviado) is on `custo_direto`: migration `20261028000031` moved the existing ones and trigger `budget_direct_cost_default` makes copies/revisions of old budgets start on it too; locked budgets keep the model they were closed with. Defaults come from `pricing_settings` (structure_rate, architect_commission, tax_rate, desired_margin, min_margin) and are copied into each new budget; structure counts as cost in `computeWorkResult`. Saving below the minimum margin asks for confirmation; nothing of the pricing area reaches the client PDF.
- Work budget × actual per stage (`BudgetVsActual`): planned = stage direct cost (`stageCosts`), actual = paid stage outflows, with `costVariance` and `unassignedStageSpent` in operations.ts.
- Budget editor layout: the Serviços tab is one "Etapas e serviços" panel whose stages collapse/expand (state per budget in localStorage, first stage open by default; search forces matches open; "Expandir/Recolher todas"), each stage header showing services/materials counts, direct cost and sale price; the pricing sidebar is sticky with its own scroll on xl (`max-h-[calc(100vh-2rem)] overflow-y-auto`) and the per-stage cost list sits behind "Ver custo por etapa". The page header, KPI cards and saved versions stay as they are.
- Budget versions (`budget_versions`): while a budget is editable (elaboração/enviado), "Salvar versão" generates the official PDF through the API, stores it in `jmg-documents/budget-versions/` and inserts a numbered version (number, guards and author set by the database; closed budgets refuse new versions). Approval saves a version first when the content fingerprint (`budgetFingerprint`, ignoring status and edit timestamps) changed, and trigger `mark_approved_budget_version` marks the latest version as approved. Versions are never edited.
