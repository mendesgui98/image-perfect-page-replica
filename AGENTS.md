# Regras do projeto JMG Obras

Desenvolvimento direto pelo GitHub (sem Lovable). Trabalhe em branches e abra PR para a `main`; o CI precisa passar.

## Project rules

- All price/margin math lives in `src/lib/pricing.ts` (pure, tested in `pricing.test.ts`); UI and PDF only call `computeBudget` — never duplicate formulas.
- Budget items snapshot catalog costs/composition (jsonb `materials`) so catalog edits never silently change existing budgets.
- Cost data access is enforced by RLS via `public.can_see_costs()` (admin/financeiro); roles live in `user_roles`, never on profiles.
- Approved/refused/superseded budgets are locked by DB trigger; changes go through "Reabrir para edição" (`copy_budget(id, true)` revisions, reusing an open newer revision via `openRevision`). Approving a revision (trigger `supersede_previous_budget`) atomically marks the previous approved version `substituido` (`superseded_by`), moves the linked work's `linked_budget_id` and stage sections to it, and is refused when that work has a signed contract (use extras instead).
- Works use the shared record trash (`manage_record_deletion` with `work_registry`): trashing also trashes the linked schedule header; permanent deletion is refused while financial, purchase, contract, record, extra or estimate links exist. Work list readers filter `deleted_at`.
- Client PDF is an HTML print view (`/orcamentos/$id/pdf`) styled after the client's model; it must never render internal costs/margins.
- work_registry is canonical for both origins; linked_budget_id alone references an immutable approved budget (only the supersede trigger may move it within the same budget family). Legacy works mirrors conversion atomically to preserve identifiers; direct works never insert budgets.
- Operational quantities and cash/allocations use pure tested helpers in operations.ts and work-opening.ts; economic price/result calculations stay in pricing.ts.
- Uploaded evidence and work documents use the private `jmg-documents` bucket and temporary signed URLs; team access is limited to operational records.
- Purchases create commitments atomically; partial receipts determine incurred purchase cost, while settlements affect only cash, never a second expense.
- Contract wording comes from the supplied model; saved bodies are snapshots and signed contracts/approved extras are immutable.
- Unconfirmed completion estimates retain the unregistered original budget cost; never interpret absent estimates as zero remaining cost.
- Work, contract, schedule, diary and extra changes append database audit snapshots in work_history so revisions retain authorship and prior values.
- Opening snapshots are immutable and separate from transactions and account balances; direct-work forecasts stay unconfirmed until a completion estimate is entered.
- Financial dashboard aggregation is shared by company and work views; economic results use pricing helpers, and installment payables never add a second purchase expense.
- Form drafts are scoped to the signed-in user and form on the current device; restore installment values but require users to reselect attachments.
- Draft capture and restoration use the shared form-draft helpers, including explicit unchecked values and file exclusion, so forms preserve selections consistently.

- Executive indicators and financial drilldowns use executive.ts compositions from dashboard-data; totals and source rows share one selector to prevent divergence.
- Relationship screens reuse relationship-data queries and navigate to existing work editors; the person profile route is unnested from the directory list to render independently.
- Record deep links use entry/record search parameters and use-record-focus to reveal the source without mutating transactions.

- Work progress/status comparisons live in pure tested work-progress.ts; shared dashboard progress preserves the immutable opening reference until weighted stages exist.
- Stage photos are existing work_records linked by stage_id, protected by same-work validation and private records paths; gallery and reports reuse these rows, so uploads are never duplicated.
- Individual work metrics use work-composition.ts to extend executiveComposition; signed economic breakdowns use the pricing result fields without recomputing economic formulas.
- Schedule headers identify all plans: standalone stages/versions live on schedules/schedule_versions until atomic linking moves stages with stable IDs and preserves immutable versions in work_stages/work_schedule_versions; linked plans always edit work_stages, never a second copy. Removed work stages remain for audit but all operational readers filter them out. Schedule date/status helpers and Gantt are shared with client print views.
- Enter submits forms through the global EnterToSubmit rule in enter-submit.ts (textarea only with Ctrl/Cmd+Enter); dialogs use SubmitForm with a type="submit" save button, every other button is type="button", and onBlur inline fields use commitOnEnter.
- CPF/CNPJ, RG, telefone e CEP são pontuados por `src/lib/documents.ts` na digitação, no salvamento e na exibição; campos de nome/endereço usam `capitalizeWordsProps` de `src/lib/text-case.ts` (maiúscula na letra digitada no início da palavra, partículas da/de/do minúsculas).
- Finance separates cash from accounts: `financial_settlements` are the realized cash movements and `financial_entries` the receivables/payables. Cash-only movements go through `register_cash_movement` (entry + settlement, `cash_only`), reversals through `undo_settlement`, cancellations through `cancel_financial_entry`; balances/status come from `cashSummary`/`accountStatus` in operations.ts.
- Stage services (`work_stage_services`) hold planned labor/material and progress; stages without services use the typed planned labor/material in `work_stage_values` (cost data, can_see_costs RLS, audited), which `stageCosts` ignores once services exist so values never double count; budget conversion (`convertBudgetToWork` → `convert_budget(id, services)`) creates one stage service per budget item with its COST (labor/material from computeBudget), mapped to its section's stage in the same transaction; an approved revision re-syncs them with `syncBudgetStages` → `sync_budget_stage_services` (lineage via `budget_items.origin_item_id` and `work_stage_services.budget_item_id`: updates cost/description keeping progress, adds new items/sections, deletes removed ones; manual services untouched); after conversion and after that sync, `applyValueWeights` sets each stage's weight ("Avanço % da obra") proportional to its planned value via the pure `valueWeights` (work-progress.ts, sums exactly 100%); stage progress is the value-weighted `servicesProgress` written to `work_stages.progress`, and stage spending comes only from finance outflows with `stage_id` via `stageCosts` — never a second manual cost field.
- Work checklist (`work_checklist_items`, aba Checklist da obra): each stage service becomes an item automatically via trigger `sync_checklist_from_service` (description/stage follow the service; deleting the service deletes the item), the team may add standalone items; RLS like work_stages (admin/financeiro/equipe) so the team never reads service costs; `checked_at`/`checked_by` are set by the database; checking never changes stage progress or finance. Grouping/counting use pure `work-checklist.ts`; the per-stage print view is `/obras/$id/checklist/pdf?stage=`.
